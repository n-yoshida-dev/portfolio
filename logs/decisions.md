# 判断ログ

議論で到達した判断と、その理由・却下した代替案の台帳。
同じ論点を後で蒸し返さないために残す。新しいものほど上にある。

ここに書くのは**ユーザーと合意した判断**（方針・スコープ・生活の前提・複数案から選んだ設計）。
Claude が実装中に選んだ技術的な選択とハマりどころは `KNOWLEDGE.md`。やることは `TODO.md`。
追記は `/decide`。新しいエントリは下の `---` の直後に入れる（`/decide` がそうする）。

1 エントリの形式（`/decide` と同じ。1 エントリ 1 判断）：

```
## YYYY-MM-DD <論点を一言で>

**論点**: 何を決めようとしていたか
**結論**: どう決めたか
**理由**: なぜその結論にしたか
**却下した代替案**: 検討して捨てた選択肢と、捨てた理由（なければ「なし」）
**確信度**: 高 / 中 / 低
**見直す条件**: この前提が崩れたら判断をやり直す、という条件（なければ「なし」）
```

---

## 2026-09-26 非公開リポジトリの構造は「概念レベルの区分」までなら書いてよい

**論点**: Systems の「Personal AI Context System」が、非公開リポジトリの中の構造（入口 / 詳細 / 履歴 / メタ の 4 区分）まで説明している。README の線引き「Private リポジトリは存在と目的だけを書く」に照らして、この粒度を許すか
**結論**: 許す。区分の名前と役割（何のための層か）までは書いてよい。ファイル名・実データ・判断の経緯の固有名詞は引き続き書かない
**理由**: 「AI 向けの個人コンテキストをどう層に分けるか」は設計の考え方であり、中身が無くても読み手に価値がある。区分名だけでは個人情報に届かない
**却下した代替案**: 存在と目的だけにする（Systems ページの意味が薄くなる）
**確信度**: 高（2026-09-26 にユーザーが「このままでよい」と回答）
**見直す条件**: 区分の説明にファイル名や実データの例を足したくなったとき（そのときは書かずにこの判断を見直す）

## 2026-09-26 AI 協働で作ったものは Skills の根拠に数えない

**論点**: AI エージェントに実装を任せて作った AI Study Coach（と skill-matrix のフロント・Go バックエンド）を、React / Go / DB / CI の実力の根拠として Skills に載せるか
**結論**: 載せない。Projects には残す（featured を外す）が、Profile のリンク欄と Skills の根拠からは外し、「AI 協働開発の仕組み」の実例として 1 行だけ触れる。Go は「一時停止中」と明記する
**理由**: 自分で設計・実装した OrgFlow と、AI に書かせて自分は判断した習作を同じ欄に置くと「根拠のない『できる』を書かない」方針が崩れる。AI 協働の実例としては価値があるので削除はしない
**却下した代替案**: 完全に外す（公開済みの唯一のデプロイ実績を失う）。featured のまま残す（React の根拠に見えてしまう）
**確信度**: 高
**見直す条件**: 自分で React / Go のコードを書いて理解を確認した根拠ができたとき

## 2026-09-26 扱った製品名（SKYSEA Client View）は書いてよい。勤め先は書かない

## 2026-09-25 禁止語スキャンに許可リストを作らない

**論点**: `public-profile/` の禁止語スキャンで誤検知が出たとき、その行を許可するか
**結論**: 許可リストは作らない。文章を書き直すか、パターンの側を狭める
**理由**: 「この行は OK」が増え続けると検査が形骸化する。公開情報の漏えいは 1 回目で仕組み化する対象（ops の原則）なので、検査は硬いままにする
**却下した代替案**: 行末コメントで抑止する仕組み（Markdown に検査用のマークが混ざり、読み手に見える）
**確信度**: 高
**見直す条件**: 書き直しでは表現できない正当な記述が 3 回以上出たとき

## 2026-09-25 Astro（静的出力）を採用し、サイトをリポジトリ直下に置く

**論点**: 技術構成（ユーザーの想定は Next.js + TypeScript + Vercel）と、apps 共通の `frontend/` `backend/` 構成に従うか
**結論**: Astro + TypeScript + 素の CSS。静的出力で Vercel に置く。サイトはリポジトリ直下
**理由**: 内容が Markdown で、サーバー処理が無い。Astro は Markdown を主役に置く設計で、`/llms.txt` や各ページの `.md` 版を 1 ファイル 1 エンドポイントで作れる。
JavaScript を出さないので速く、ライブラリが増えない。バックエンドが無いので `frontend/` に分ける意味がなく、Vercel の設定も減る
**却下した代替案**: Next.js（API・SSR 前提の機能が多く、この用途では保守対象が増える）、React + Vite（Markdown の扱いと `.md` 出力を自前で組むことになる）、GitHub Pages（PR ごとのプレビューと独自ドメインの扱いで Vercel が楽）
**確信度**: 高（ユーザーは「Next.js が過剰なら代案を出してよい」と明示）
**見直す条件**: 訪問者の操作に応じて動く画面（自前の Ask AI など）が必要になったとき。そのときも Astro に React を部分的に足す形で足りる見込み
