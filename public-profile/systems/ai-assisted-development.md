## 何を解いているか

AI に実装を手伝わせると速くなる一方で、「何を作るか」「何を決めたか」「今どこか」が会話の中に埋もれます。
セッションが変わるたびに文脈が消え、同じ議論を蒸し返し、意図と違うものが完成扱いになります。

このワークフローは、**文脈をリポジトリの文書に固定し、検証を機械に任せ、人間は判断だけをする**ように組んだものです。

## 1. ワークスペースを 5 つに分ける

| ルート | 用途 |
|---|---|
| apps | 完成させて公開する自作アプリ。アプリごとに独立リポジトリ |
| study | 学習（非公開） |
| writing | 記事の執筆と公開の工程管理（非公開） |
| ops | 家計・タスク・メールなどの雑務（非公開） |
| personal | 自分に関するデータ。AI 向けコンテキスト、読書記録 |

ルートごとに CLAUDE.md（AI への指示書）を置き、目的・ルール・禁止事項を固定します。
ルートを跨ぐ作業はしません。

## 2. 各アプリが持つ文書（AI 向け）

| 文書 | 役割 |
|---|---|
| PLAN.md | 何を作るか・なぜ作るか。走り書きでよい |
| SPEC.md | 確定した仕様。実装が参照する正本 |
| TODO.md | タスク。1 タスク = PR 1 本。各タスクに「完了条件：」を付ける |
| KNOWLEDGE.md | ハマったこと、AI が実装中に選んだ技術判断 |
| HANDOFF.md | 現在地と次の一手だけ（目安 40 行）。履歴は積まない |
| logs/decisions.md | 人間と合意した判断の台帳。設計を提案する前に読む。同じ論点を蒸し返さない |

同じ事実を AI 向けと人間向けの両方に書きません。設計判断の理由は ADR（OrgFlow）や KNOWLEDGE に置き、README からはリンクだけにします。

## 3. フックとスキルで手順を機械化する（claude-plugins）

```
セッション開始 → TODO からフェーズ別の進捗表を自動提示
ファイル編集   → 直後に typecheck / lint / go vet を自動実行
git commit     → ステージ済みファイルに秘密情報があればブロック
区切り         → /handoff が HANDOFF / TODO / KNOWLEDGE / 判断台帳を更新
```

複数のアプリで同じ設定を使うため、リポジトリごとにコピーせず [プラグイン](/projects/claude-plugins)として 1 か所で管理します。

## 4. PR からマージまで

```
ローカルで CI と同じ検査 → PR（本文に「完了条件」と「確認した証拠」を 1 行ずつ）
  → CI（format / lint / typecheck / test / build / 秘密情報スキャン）
  → 受け入れレビュー役（読み取り専用の AI エージェントが、差分を完了条件と仕様に照らす）
  → squash マージ（ブランチ保護。main への直接コミットはしない）
```

CI は「動くが意図と違う」を止められません。それを止めるのが受け入れレビュー役です。
人間はコードではなく「完了条件」と「証拠」を見て判断します。

## 5. 判断は人間、検算は機械

- **一番つらい工程だけ自動化し、最終確認は人間が行う**。完全自動化は狙わない
- **検証（見落とし探し）だけは機械にやらせる**。新しい業務を作るときは「AI が自分で正誤を確かめられる手段」を 1 つ用意する
- **同じ気づきが 3 回出たら手順書に昇格する**。ただし機密の扱いとデータを壊す操作は 1 回目で昇格する
- **止まるのは限られた場合だけ**。生活の前提、破壊的な操作、作るものの範囲が変わる判断、お金が掛かる操作。それ以外は進めて事後報告する
- **AI の生成コードは、設計理由と主要処理を自分で説明できるまでレビューする**

## 6. 失敗から直したこと

- **利用者が触る面を先に通す**：skill-matrix で、着手から 6 週間・実装 24 件のうち画面が 0 件で、当初の目的である可視化を一度も試せていなかった。
  以後、「誰が使うか」を最初に決め、画面・CLI・出力ファイルのどれかを早い段階で 1 つ通す
- **HANDOFF は現在地だけ**：あるアプリで 23 行が 1 か月で 397 行になり、読むだけでコンテキストを食っていた。履歴は git log と PR に任せる
- **install 忘れは静かに死ぬ**：プラグインの設定を書いただけで install されておらず、3 アプリが 8 日間フックなしで動いていた。確認手順を README に残した
- **PR 作成と CI 待機を同じコマンドに繋げない**：CI の登録が遅れて、CI 前にマージした事故があった

## 7. クラウドでの定期実行

一部の雑務（毎朝のメールトリアージ）はクラウド上の定期実行（ルーチン）に任せています。
ルーチンはリポジトリを読み、README を判定基準として動きます。**基準を変えるときは README を直して push する**だけで、
プロンプトには認証情報や投稿先など、リポジトリに書けないものだけを残します。
